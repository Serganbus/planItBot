СТРОГИЕ ПРАВИЛА
═══════════════════════════════════════════
1. declare(strict_types=1); везде. Typed properties, readonly DTO, enums.
2. Никакой бизнес-логики в контроллерах и в handler'е Telegram.
3. В очередь НИКОГДА не класть Request, Closure, Eloquent-модели с связями
   или объекты Telegraph. Только scalar/массив payload или сериализуемый DTO.
4. Webhook должен быть идемпотентным: повторная доставка update_id
   не должна дублировать задачи или повторные сообщения.
5. chat_id Telegram = BIGINT (не int, не unsigned), всегда проверять
   принадлежность задачи чату/пользователю — защита от IDOR.
6. Не использовать reflection для изменения readonly-свойств planner-cli.
   Доменные сущности переписываем на собственные immutable-объекты.
7. Для тестов — Pest. Для каждого шага — минимум: happy path + negative case.
8. Секреты только через env/config, никогда не хардкодить токен.

ШАГ 2. СХЕМА ДАННЫХ POSTGRESQL
═══════════════════════════════════════════
Миграции + Eloquent-модели + PHP-enum'ы:

chats:
  chat_id bigint PK (без auto_increment),
  timezone string default 'UTC', language string default 'ru',
  settings jsonb default '{}',
  goal_date date nullable, main_goal text nullable,
  created_at / updated_at

tasks:
  id uuid PK (генерируется в PHP/DB, не bigint),
  chat_id bigint FK -> chats ON DELETE CASCADE,
  task_date date NOT NULL,
  type string + CHECK in (scheduled, flexible, goal),
  title text, scheduled_time time nullable,
  estimated_minutes smallint nullable, priority smallint default 0,
  tags jsonb default '[]' (cast => array),
  status string + CHECK in (pending, completed, cancelled),
  telegram_message_id bigint nullable,
  created_at / updated_at / completed_at nullable

dialog_states:
  chat_id bigint PK FK,
  flow string, step string, payload jsonb default '{}',
  expires_at timestamp nullable, updated_at

telegram_updates (идемпотентность):
  chat_id bigint, update_id bigint,
  UNIQUE(chat_id, update_id), processed_at nullable

Индексы:
  - tasks(chat_id, task_date, status)
  - tasks(chat_id, type)
  - GIN-индекс по tags
  - частичный индекс по pending-задачам

Поясни, почему используешь string + CHECK вместо нативного PG enum
(проблема ALTER TYPE при миграциях).
КРИТЕРИЙ ПРИЁМКИ: migrate и migrate:rollback проходят на чистом PostgreSQL.

ШАГ 5. WEBHOOK + QUEUE (САМЫЙ ВАЖНЫЙ ШАГ)
═══════════════════════════════════════════
Схема потока:
Telegram POST -> WebhookController -> запись update в БД (идемпотентно)
             -> dispatch(ProcessTelegramUpdateJob) -> HTTP 200 (<50 мс)
Queue worker -> Domain Services -> Telegraph (ответ/правка сообщения/клавиатура)

Файлы:
- app/Http/Controllers/TelegramWebhookController.php
  * сверь с документацией telegraph: используется ли их встроенный
    WebhookController/WebhookHandler или нужен свой тонкий приёмник;
  * проверка секретного пути/заголовка (не только токен в URL);
  * НЕ вызывать Bot API синхронно;
  * не класть Request в очередь.
- app/Jobs/ProcessTelegramUpdateJob.php
  * implements ShouldQueue, onQueue('telegram'), tries(3),
    backoff([5, 30, 120]), uniqueId по update_id;
  * DB-транзакция + UNIQUE(chat_id, update_id) как второй уровень защиты;
  * маршрутизация: command -> DialogStateMachine,
    callback_query -> PrefixCallbackDispatcher,
    web_app_data -> Application-обработчик Web App.
- app/Application/Telegram/PlannerUpdateRouter.php — собственный диспетчер.
- app/Application/Telegram/KeyboardFactory.php — адаптация src/Keyboard.
  * callback_data строго <= 64 байта (mb_strlen по байтам, не по символам!),
    формат: "act:verb:8hex", например "t:done:3f2a91c0".
- app/Application/Telegram/DayViewRenderer.php — адаптация src/View.

Настройка webhook: использовать artisan-команду пакета для set-webhook
(точное имя проверить через artisan list), HTTPS, секретный путь,
close old polling через deleteWebhook/setWebhook корректным образом.
Приложить systemd/supervisor конфиг для queue:work --queue=telegram
с --tries и restart.
КРИТЕРИЙ ПРИЁМКИ: тест контроллера отвечает 200 за <50 мс при
заблокированной БД; повтор update_id не создаёт вторую задачу.

ШАГ 6. TELEGRAM WEB APP BACKEND
═══════════════════════════════════════════
- app/Http/Middleware/ValidateTelegramWebApp.php
  Алгоритм проверки (именно такой, не иной):
  1. Берём initDataRaw (заголовок X-Telegram-Init-Data или тело запроса).
  2. Парсим query string в пары, убираем hash, сортируем ключи лексикографически.
  3. data_check_string = "key=value" через "\n".
  4. secret_key = hash_hmac('sha256', BOT_TOKEN, 'WebAppData', true)
     ВНИМАНИЕ: 'WebAppData' — ключ, токен — данные. НЕ hash('sha256', token)!
  5. calculated = hash_hmac('sha256', data_check_string, secret_key)
  6. hash_equals(calculated, received_hash), иначе 403.
  7. Проверяем auth_date: возраст не больше 1 часа (настраиваемо), иначе 401.
  8. Декодируем user, кладём в request attributes ТОЛЬКО проверенные
     id/username; chat_id берём из сессии/привязки, не из тела запроса.
- app/Http/Controllers/Api/WebApp/TaskController.php:
  GET    /api/webapp/day?date=Y-m-d
  POST   /api/webapp/tasks
  PATCH  /api/webapp/tasks/{uuid}
  DELETE /api/webapp/tasks/{uuid}
  POST   /api/webapp/goal
- Маршруты в routes/api.php, middleware ['telegram.webapp', 'throttle:60,1'].
- Фронтенд Mini App: только статические ассеты + вызовы API с initDataRaw.
  Никакой бизнес-логики на клиенте.
- В боте кнопка открытия через Telegraph::webApp(...) / WebAppKeyboardButton
  (сигнатуру сверить с установленной версией).
КРИТЕРИИ ПРИЁМКИ: тесты — валидная подпись, поддельная подпись,
просроченный auth_date, чужой chat_id (IDOR), отсутствие заголовка.
